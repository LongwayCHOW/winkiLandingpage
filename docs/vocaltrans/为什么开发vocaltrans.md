# 为什么开发vocaltrans

> **用途**：我在去年旅行之后，加入一个Reddit社群 r/travelchina/ 之后，开始热心地回复其他国外用户关于“中国旅行”的问题，在社群活跃的过程中，我逐渐意识到，很多人在中国旅行时，语言是一个非常大的障碍，而他们所依赖的【翻译app】依赖手机设备对互联网的访问才能正常工作，而用户常常意识不到这个技术问题，或者意识到了也没有解决复杂的手机跨地区网络访问的问题，甚至是，他们的 vpn 没有正常测试过或者突然无法正常工作了...
这经常造成非常大的麻烦，我还看到有的国外旅客凌晨1点才下机场，然后因为语言沟通问题找不到酒店，而拉着行李箱在街道上很迷茫地游荡（虽然中国很安全，但是这也天可怜了太无助了）。
这让我萌生了“开发一个值得信赖的离线翻译app”供访问中国的游客使用。

## 核心素材（请围绕一个"冲突或取舍"展开）

1. **一个真实的技术挑战**：
A、能提供离线翻译能力的基础模型选择不多
B、在如此选择有限的翻译模型的基础上，能在手机上离线运行的就更少了
C、使用顶尖配置的手机的游客毕竟是少数，离线翻译模型需要很强的运行配置，以及吞噬大量的运行内存
D、离线模型由于运行环境的限制，被极大地压缩/减少参数，导致真实使用的时候，经常出现小的翻译错误

2. **你尝试了什么方案**？尝试了Facebook、tencent、bitdance、Google等等各大公司的离线翻译模型
3. **最终怎么解决的**？最后选择Google的翻译模型，离线翻译从3s翻译完毕➡️1s翻译完毕，极大优化交互体验
4. **一个设计取舍**：
为什么选 Google的方案 放弃 Facebook、tencent、bitdance？
原因如下：
A、更小的模型体积，覆盖更多设备，提供离线翻译能力
B、翻译失误的问题可以通过交互解决一部分，来弥补模型小带来的翻译错误
C、通过多个小模型接力/切换，可以提供多语言翻译能力，甚至组起对话对
D、用户只买一个app，就拥有更多的翻译能力，对客户来说是一种更为实惠的选择

5. **过程中学到的教训**（对同行或用户都有价值的思考）：不断探索、学习，在 ai 时代耐心看技术文档还是很有必要的
